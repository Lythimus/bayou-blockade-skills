# SONRIS Operator Code Lookup

SONRIS files nearly everything — well permits, injection/disposal-well applications,
orders, inspections, coastal use permits, mineral leases — under an **operator code**
(e.g. `H1166` = High West Sequestration LLC, `L1126` = Lapis Energy (LA Development), LP),
not a free-text company name. Every other `sonris-*` skill needs this code as input, so
this is usually the first SONRIS skill in a chain: `sonris-operator-lookup` →
`sonris-doc-search` / `sonris-well-lookup` / `bayou:la-class-vi`.

**Operator codes aren't well-specific.** They identify any entity DNR (now the Dept. of
Conservation and Energy) has issued something to — a well operator, but also a coastal
permit holder, a mineral lessee, or a petrochemical/industrial site that happens to run an
on-site Class I hazardous-waste injection well. A refinery or chemical plant that has no
SONRIS-regulated activity at all (no wells, no coastal permit, no mineral lease) simply
won't have an operator code — that's expected, not a failed search; its air/water/waste
permit history lives in `bayou:ldeq-edms-search` / `bayou:ldeq-permit-status` instead, which
this skill should point to when a lookup here comes up empty for an obviously large
industrial name.

## Step 1 — check the seed list first

```bash
rg -i "COMPANY NAME OR FRAGMENT" ~/.claude/plugins/bayou/skills/sonris-operator-lookup/references/known-operators.md
```

Covers the Class VI/CCS operators already resolved from prior sessions. If it hits, use
that code directly — no network call needed. If the name is close but not exact, still
treat it as a candidate match and confirm with the user rather than assuming.

## Step 2 — check the DCE Class VI tracking page (name cross-reference, no code)

For anything CCS/injection-adjacent, `bayou:la-class-vi`'s source
(`https://www.dce.louisiana.gov/page/class-vi-permits-and-applications`) lists operator
names against wells/parishes — useful to confirm you have the operator's *exact
registered name* (SONRIS is picky about this) even though it doesn't give the code
directly. A resolved exact name makes Step 3 far more reliable than a guessed one.

## Step 3 — live SONRIS lookup (needs a session; the exact endpoint isn't nailed down yet)

> **Status as of 2026-08-15: exploratory.** Unlike `bayou:ldeq-ai-lookup` (which has a
> confirmed JSON POST endpoint for AI-number search), no equivalent direct
> operator-name-search endpoint for SONRIS has been confirmed yet. The document search
> app's own UI must have one — the user's original example URLs
> (`UPPER(xOperatorCode) = 'H1166'`) were generated by *some* form that resolved a
> company name to that code — it just hasn't been reverse-engineered.

Confirm a session first (`bayou:sonris-session`, `--check`), then open the document
search app's root and look for the operator field itself:

```bash
node ~/.claude/plugins/bayou/skills/sonris-session/sonris_get.js \
  --url "https://sonlite.dnr.state.la.us/ords/r/sonris_pub/document_access/" \
  --throttle 2500
```

Read the returned HTML for an operator name/autocomplete field. Oracle APEX pages like
this commonly back such a field with a small AJAX "list of values" call — if the HTML
references one (look for `wwv_flow.ajax` or a fetch/XHR call tied to the operator input),
that's the real endpoint; note it here with today's date once confirmed, including its
exact request shape, and convert this step into a direct `curl`/`sonris_get.js` call like
`ldeq-ai-lookup` — don't leave it as a manual HTML-read step once a real endpoint is
found.

If reading the HTML doesn't surface it cleanly, this is one of the few places using the
operator field by hand is worth it: with the document search app open in a real browser
(the same session `bayou:sonris-session` capture already came from, or a fresh
`sonris_session.js --headful` if one's needed), use the operator field once and watch
DevTools → Network for the request it triggers. If the user is comfortable with
DevTools, `node ~/.claude/plugins/bayou/skills/sonris-session/sonris_session.js` (no
args) will parse a "Copy as cURL" of that exact request directly — same capture flow
already used to establish the session, so no separate mechanism to explain. Note the
resolved endpoint here once confirmed, so it can be hardcoded permanently. This only
needs to happen once, ever — after that, this skill should never need a live browser
again.

## Presenting results

- **Exact single match**: operator code (prominent), full registered name exactly as
  SONRIS has it, and — if visible in whatever response is available — status/address if
  offered.
- **Multiple candidates**: numbered list, ask the user to confirm.
- **No SONRIS match at all**: say so plainly, and if the name is a large industrial
  facility, suggest `bayou:ldeq-ai-lookup` instead — SONRIS not having a record for a
  petrochemical plant with no wells/coastal permits/mineral leases is a legitimate,
  expected outcome, not a dead end.
